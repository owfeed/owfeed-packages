# Ранбук

*[English version](RUNBOOK.md)*

Что делать, когда в автоматике фида что-то сломалось. Для дежурного мейнтейнера.
Про добавление и обновление пакетов — [CONTRIBUTING_ru.md](CONTRIBUTING_ru.md).

- **Ключ подписи** использует только второй publish-job на `main`, который идёт за
  `environment: feed`. Сами ключи — секреты репозитория.
  Pull request'ы и ветки `update/*` работают с одноразовыми ключами.
- **Доверенное обновление не открывает PR.** Плановый job пушит `update/<пакет>-<версия>` и
  запускает на ней `Check`. Следующий прогон `land-updates.sh` переводит на неё `main` fast-forward'ом.
- **Гейт — `land-updates.sh`.** Он пропускает ветку, только когда её проверки зелёные, а диф
  называет только `packages/<имя>/upstream.sh`.
- **Каждый плановый шаг идемпотентен.** Он подбирает то, что оставил предыдущий прогон, поэтому
  интервал cron ни на что не влияет.

## Быстрый поиск

| Симптом | Раздел |
|---|---|

| Незнакомая версия в `main` или в pull request'е | [Появилось обновление, а версию я не узнаю](#появилось-обновление-а-версию-я-не-узнаю) |
| Ветка `update/*` никак не доезжает | [Ветка обновления не доезжает](#ветка-обновления-не-доезжает) |
| Publish-job красный или Pages не обновились | [Публикация упала](#публикация-упала) |
| Нужно увидеть то, что видят роутеры | [Посмотреть, что видят подписчики](#посмотреть-что-видят-подписчики) |
| Вы двигаете версию owfeed | [Переход на новый релиз owfeed](#переход-на-новый-релиз-owfeed) |

## Что когда запускается

| когда | что | ключ есть? |
|---|---|---|
| pull request | fetch → build → sign → index → check-tree → check-origin → sources → doctor → smoke (обе линии) | одноразовые |
| push в `main` | job 1: fetch → build | **нет** |
| | job 2: sign → index → check-tree → check-origin → sources → smoke → verify → publish → Pages | **да**, за `environment: feed` |
| плановый прогон | перевести `main` на любую ветку `update/*`, у которой проверки уже зелёные | нет |
| | спросить у каждого апстрима свежий релиз, запушить ветку обновления, если он есть | нет |
| | запустить `Check` на этой ветке: сам GitHub для неё запуск не создаёт | одноразовые |
| | открыть PR — только если обновление не из тех, что доезжают без человека | нет |
| | запустить `Publish`, если для головы `main` нет своего запуска `Publish` | нет |

`update.yml` просит `cron: '17 * * * *'`. GitHub даёт меньше: плановые прогоны 2026-09-04..06
приходили с интервалом от двух до пяти часов.

Строка про pull request — не второй пайплайн. `pr.yml` и `publish.yml` вызывают reusable `feed.yml`
из owfeed на одном и том же пине. `pr.yml` передаёт `dry-run: true`. `publish.yml` передаёт
`secrets: inherit` и без dry-run. Разница — одноразовые ключи, отсутствие environment и отсутствие
деплоя.

<details>
<summary>Почему <code>main</code> разделён на два job'а</summary>

fetch исполняет значения, пришедшие из pull request'а, и в том job'е ключа нет. Ключ появляется,
когда собранные байты уже лежат в артефакте.

</details>

## Пакет пропал

`tools/check-tree.sh` запускается после `owfeed index` в обоих воркфлоу. Он валит прогон, если пакет,
который эта репа ингестит, отсутствует на релиз-линии, которую он объявляет.

```
MISSING luci-theme-footstrap luci-theme-footstrap_0.11.6-r1_all.ipk on 24.10: absent from 36 of 36 architecture(s) (e.g. armeb_xscale)
```

| В сообщении | Причина | Что делать |
|---|---|---|
| нет на *всех* архитектурах | Фетч не дал ничего. В релизе нет такого ассета, либо в `upstream.sh` не задан `ARTIFACT_IPK` у пакета, который раньше его публиковал. | Проверьте ассеты релиза и `upstream.sh`. |
| нет на *части* архитектур | Сборка не доехала. | Ищите в логе шаг, который упал, не остановив прогон. |

<details>
<summary>Зачем эта проверка</summary>

Пропавший пакет больше никто не видит. `owfeed doctor` читает дерево и спрашивает, верно ли то, что
там лежит. Пакета, который не скачался, там просто нет, и все проверки зелёные. Так дерево с одним
пакетом из трёх на линии 24.10 однажды отчиталось готовым к публикации.

</details>

## Проверка красная

Один и тот же workflow отчитывается и на pull request'ах, и на ветках `update/*`. Читайте находку:
каждая говорит, чем это грозит и что делать. Ниже — находки, причину которых трудно угадать.

### `OWF207`: конфигурация шипается, но не объявлена

- **Причина:** пакет ставит `/etc/config/foo`, а в `conffiles:` его нет.
- **Чем грозит:** sysupgrade читает `.conffiles_static`, чтобы решить, что переживёт обновление
  прошивки. Ваши дефолты заменят настройки пользователя при каждом обновлении, и никто об этом не
  сообщит.
- **Что делать:** добавьте файл в `conffiles:`.

### `smoke` упал, а `doctor` прошёл

Дерево согласовано, а роутер его не принимает. Смотрите вывод контейнера. Обычные причины:

- зависимость, которая не резолвится на стоковом образе;
- файл, положенный туда, куда никто не смотрит.

### `!! upstream outage: …` и код выхода 8 на шаге fetch

- **Причина:** GitHub или другой апстрим отвечал 5xx, 429, не отвечал вовсе или не резолвился. Так
  было пять попыток подряд, около 75 секунд. С пакетом ничего не нашлось.
- **Что делать:** когда [githubstatus.com](https://www.githubstatus.com) позеленеет, перезапустите
  job.

То же сообщение печатают `check-updates.sh`, `land-updates.sh` и intake — все ходят через
`tools/net.sh`. В старом прогоне вместо него может быть шесть строк
`curl: (22) The requested URL returned error: 500` и `exit code 22`. Это тоже сбой апстрима и тоже
перезапуск.

### `curl: (22) … 404` и код выхода 7 на шаге fetch

- **Причина:** файла нет в релизе. В `upstream.sh` неверный тег или имя файла, или апстрим его
  удалил.
- **Что делать:** проверьте тег и имя файла в `upstream.sh`. Перезапуск даст тот же ответ.

### `sha256 … pinned …` на шаге fetch, код выхода 7

- **Причина:** апстрим подменил релиз на месте.
- **Что делать:** сначала выясните, почему изменились байты. Не правьте пин, чтобы прошло.

### `NO ORIGIN …` от `tools/check-origin.sh`

Проверка идёт после сборки индекса.

- **Причина:** пакет дошёл до дерева, не сказав, откуда он. Этот фид его не публикует.
- **Что делать:** напишите апстриму. Поле ставится там, где пакет собирается, поэтому здесь это не
  чинится.

Значение вида `feeds/base/<name>` валится так же, как пустое. Это путь, из которого собирал SDK, и
пользователю туда не пойти.

### Упал `tools`

- **Причина:** покраснел самотест одного из скриптов в `tools/`, и `check` не запустился. В логе
  рядом со сломанным случаем стоит `FAIL`.
- **Что делать:** прежде чем пушить правку в `tools/`, прогоните тесты у себя. Им нужны `git` и
  `jq`, в сеть они не ходят.

```sh
sh tools/test-sources.sh
sh tools/test-land-updates.sh
sh tools/test-check-updates.sh
sh tools/test-net.sh
```

## Появилось обновление, а версию я не узнаю

1. Посмотрите диф — неважно, пришёл он pull request'ом или коммитом в `main`. Там должна быть
   версия и её суммы, больше ничего.
2. Если задето что-то ещё, проблема в боте, а не в релизе. `tools/land-updates.sh` такой push бы
   отверг, так что в `main` эта форма означает, что коммит положил человек.

Как придержать обновление:

| Обновление | Что делать |
|---|---|
| без pull request'а (доверенное) | Поставьте `AUTO_MERGE="no"` в `upstream.sh` пакета. |
| получило pull request | Закройте его. Бот не переоткроет его и ветку не пересоберёт. |

`AUTO_MERGE="no"` — единственный надёжный способ придержать доверенное обновление. Оно доезжает на
первом плановом прогоне после того, как его проверки позеленели, и закрывать там нечего.

## Ветка обновления не доезжает

Ветка `update/*`, которая не доезжает, — это красная проверка: читайте прогон. В логе планового
job'а бывают ещё две формы:

| Строка в логе | Что значит | Что делать |
|---|---|---|
| `not green yet` с контекстом в состоянии `cancelled` | Отменённый прогон остался на коммите. | Удалите ветку. Следующий прогон пересоберёт её и запустит проверки заново. |
| `REFUSED` | Ветка трогает путь, которого обновлению трогать нельзя. | Это уже к человеку. |

## Публикация упала

`publish.yml` вызывает переиспользуемый workflow owfeed, `owfeed/owfeed/.github/workflows/feed.yml`.
Его job `build` работает без ключа. Job `publish` держит ключ и выполняется в окружении `feed`.

1. Откройте упавший прогон `Publish` и найдите красный шаг в таблице ниже.
2. Устраните причину по разделу, который называет таблица.
3. Перезапустите упавшие job'ы со страницы прогона или командой `gh run rerun <run-id> --failed`.

- **Артефакт сборки хранится один день** (`retention-days: 1`). Позже перезапуску `publish` нечего
  скачивать. Запустите новый прогон: `gh workflow run publish.yml --ref main`.
- **Одобрение:** окружение `feed` решает, ждёт ли `publish` ревьюера. Если у него есть обязательные
  ревьюеры, одобрите job на странице прогона. Пустой список от этой команды значит, что job
  стартует сразу:

  ```sh
  gh api repos/owfeed/owfeed-packages/environments/feed --jq .protection_rules
  ```

### Какой шаг упал

Шаг без имени GitHub показывает как `Run` и его команду.

| Job | Шаг | Что выполняет | Раздел |
|---|---|---|---|
| `build` | `Run bash -euo pipefail -c "$SCRIPT"` | `pre-build`: `./tools/fetch.sh` для каждого пакета | строки про fetch в [Проверка красная](#проверка-красная) |
| `build` | `Run owfeed --frozen-lock build` | `owfeed build` по `owfeed.lock` | [Что намеренно не автоматизировано](#что-намеренно-не-автоматизировано), покрытие архитектур |
| `publish` | `Check a signing key is reachable` | выходит с кодом 4, когда `OWFEED_SIGN_KEY` пуст | [Частые причины](#частые-причины) |
| `publish` | `Sign and index` | `owfeed sign`, `owfeed index` | [Частые причины](#частые-причины), [Коды выхода](#коды-выхода) |
| `publish` | `Run bash -euo pipefail -c "$SCRIPT"` | `post-index`: `check-tree.sh`, `check-origin.sh`, `sources.sh` | [Пакет пропал](#пакет-пропал), [`NO ORIGIN`](#no-origin--от-toolscheck-originsh) |
| `publish` | `Install it on a real image` | `owfeed smoke --release` для 25.12 и 24.10 | [`smoke` упал, а `doctor` прошёл](#smoke-упал-а-doctor-прошёл) |
| `publish` | `Compare against what is live` | `owfeed verify out` | [Частые причины](#частые-причины), `OWF513` |
| `publish` | `Check and publish` | `owfeed publish` | [Коды выхода](#коды-выхода), код 6 |
| `publish` | `actions/upload-pages-artifact`, `actions/deploy-pages` | деплой на Pages | [Настройки деплоя на Pages](#настройки-деплоя-на-pages-которые-ломают-живой-сайт) |

У `Compare against what is live` стоит `continue-on-error: true`. Его находки не роняют job, поэтому
читайте его лог при каждой красной или подозрительной публикации.

### Частые причины

| Находка | Причина | Что делать |
|---|---|---|
| `no signing key: set OWFEED_SIGN_KEY in the 'feed' environment` или `$OWFEED_SIGN_KEY is empty` | Секрета нет, или прогон стартовал раньше, чем секрет появился. | Перезапустите job. |
| `$OWFEED_USIGN_KEY is empty` | Нет секрета для подписи opkg. | Перезапустите job, когда `OWFEED_USIGN_KEY` задан. |
| `owfeed verify` сообщает `OWF513` | Уже опубликованная версия имеет другое содержимое, чем то, что её заменяет. Пакет изменился без поднятия версии, или сборка перестала быть воспроизводимой. | Проверьте, что `SOURCE_DATE_EPOCH` всё ещё константа. Он берётся из входа `source-date-epoch` в `feed.yml`, по умолчанию `1700000000`. `publish.yml` его не задаёт. Не публикуйте поверх: поднимите ревизию. |
| `owfeed verify` сообщает `OWF514` | Живой сайт отвечает на `/.nojekyll` не 200. | Проверьте, что шаг загрузки задаёт `include-hidden-files: true`, и перезапустите. См. [Настройки деплоя на Pages](#настройки-деплоя-на-pages-которые-ломают-живой-сайт). |
| Pages не обновились | Деплой делает `actions/deploy-pages`. | Смотрите тот job, а не фид. |

### Коды выхода

`owfeed` выходит с этими кодами, они заданы в `cmd/owfeed/main.go` в owfeed. `tools/net.sh` и
`tools/fetch.sh` используют 7 и 8 так же.

| Код | Имя в исходниках | Перезапускать? |
|---|---|---|
| 0 | OK | |
| 1 | internal | |
| 2 | config | |
| 3 | build | |
| 4 | key | |
| 5 | index | |
| 6 | publish | |
| 7 | check | никогда: проверка не прошла |
| 8 | upstream | да: сбой апстрима |
| 9 | conflict, например с `owfeed.lock` | после `owfeed lock --update` и чтения дифа |

### Настройки деплоя на Pages, которые ломают живой сайт

- **`actions/upload-pages-artifact` нужен `include-hidden-files: true`.** С v4 он выбрасывает
  dotfiles, а `.nojekyll` это dotfile. Без него Pages запускает Jekyll поверх дерева бинарей. Jekyll
  убирает всё, что начинается с точки или подчёркивания, из дерева, которое было корректным, когда
  его проверял `owfeed publish`.
- **`actions/deploy-pages` нужен `actions: read`.** Блок `permissions:`, который называет другие
  области, молча его отбирает.
- **`owfeed verify` сообщает OWF514**, когда живой сайт потерял `.nojekyll`. Снаружи деплоя —
  единственное место, где этот ответ существует. Исправление от owfeed: задать
  `include-hidden-files: true` у `actions/upload-pages-artifact`. Запиненный `feed.yml` его задаёт.

## Посмотреть, что видят подписчики

```sh
owfeed verify                 # по задокументированному URL, локальное дерево не нужно
owfeed verify out             # плюс сравнить то, что заменит опубликованное
```

`owfeed verify` забирает опубликованный ключ и индекс. Он сообщает:

- о редиректах, по которым apk не пойдёт;
- о пакетах, которые живой индекс называет, а их нет или они другого размера;
- о версиях, перепубликованных с другим содержимым.

С точки зрения роутера, одной командой:

```sh
owfeed smoke                  # ставит собранный фид на живой образ OpenWrt
```

## Переход на новый релиз owfeed

1. Убедитесь, что релиз owfeed опубликован. Если запушить `setup@vX.Y.Z`, пока тот релиз ещё
   собирается, каждый job упадёт с *«does not verify as built by owfeed/owfeed's release workflow»*.
   Читается как атака, а на деле гонка.
2. Передвиньте пин. Это одна строка в каждом workflow: `uses: owfeed/owfeed/.github/workflows/feed.yml@v0.5.8`
   в `pr.yml` и `publish.yml`, `uses: owfeed/owfeed/setup@v0.5.8` в `intake.yml`. `owfeed-version:` обратно не
   добавляйте: этот workflow ставит тот релиз owfeed, которым помечен сам.
3. Проверьте, что передвинулись все строки. Проверяйте grep'ом, а не по памяти. Он ловит любую
   мажорную версию, так что подойдёт и для v1.x. Он выводит и комментарии с версией; их не трогайте.

   ```sh
   grep -rnE '@v[0-9]+\.' .github/workflows
   ```

   Если после этого сборка падает на `owfeed.lock`, выполните `owfeed lock --update`, прочитайте диф
   и закоммитьте его в тот же pull request.

4. Откройте pull request, как для всего остального.

Если та же правка включает политику, которая требует пинов пакетов, двигайте пины пакетов тем же
коммитом. Включить `signing.author-keys`, пока пины указывают на неподписанные релизы, — значит
исключить все пакеты фида. Публикация при этом пройдёт успешно с пустым деревом, а это худшая форма
отказа.

<details>
<summary>Как сюда попадает owfeed и почему пин — на релиз</summary>

Воркфлоу используют `owfeed/owfeed/setup@v0.5.8`, пин на релиз. Action скачивает один бинарь. До
запуска он сверяет бинарь с build-аттестацией из релизного workflow самого owfeed. Контрольная сумма
из того же релиза не годится: тот, кто подменил бинарь, подменил бы и её.

`setup` отказывается ставить бинарь, который не сверяется, — в том числе тот, которого ещё нет.
Поэтому релиз должен быть опубликован раньше, чем сдвинется пин.

Раньше это был `go install …@<sha>`. Он компилировал инструмент в каждом job и не проверял ничего:
`go install` доверяет тому, что module proxy отдаст за эту ревизию.

Инструмент, который подписывает этот фид, должен двигаться, когда кто-то поменял строку, а не когда
запушили в чужой репозиторий.

</details>

## Ключи подписи

Их два, потому что каждый пакетный менеджер проверяет только свою схему:

| секрет | схема | что подписывает |
|---|---|---|
| `OWFEED_SIGN_KEY` | EC prime256v1 | apk-индекс |
| `OWFEED_USIGN_KEY` | usign / ed25519 | opkg-индекс |

- **Оба живут в секретах репозитория** и больше нигде здесь. `.gitignore` закрывает `*.pem`,
  `*.key` и `*.sec`, чтобы их нельзя было закоммитить случайно.
- **opkg-ключ** публикуется под своим id в качестве имени файла: именно так opkg его ищет.
- **apk-ключ** публикуется под именем фида. apk сопоставляет по идентичности внутри подписи, а имя
  игнорирует.

### Если ключ утёк: отзыва не существует

У apk нет ни CRL, ни срока годности, ни способа сказать «ключ мёртв». Если ключ утёк, каждому
подписчику придётся удалить его и поставить новый руками. Пути, который дотянется до роутера, выключенного в
нужный момент, нет.

### Ротация ключа

Команды ротации в owfeed пока нет: см. Limits в
[README owfeed](https://github.com/owfeed/owfeed/blob/main/README.md#limits). С owfeed v0.4.0
`signing.also-sign` подписывает индекс вторым ключом, а `signing.keyring-package` доставляет новый
публичный ключ на роутеры. В `owfeed.yml` этого фида не задано ни то, ни другое. Измеренная
последовательность описана в
[apk-behaviour.md](https://github.com/owfeed/owfeed/blob/main/docs/apk-behaviour.md#a-keyring-package-cannot-start-a-rotation-on-its-own).
Кратко:

1. Сгенерируйте новый ключ.
2. Опубликуйте оба публичных ключа на время перекрытия.
3. Подписывайте индекс обоими.
4. Уберите старый.

apk сопоставляет ключи по идентичности, а не по имени файла. Несколько ключей сосуществуют на
устройстве, так что перекрытие ничего не стоит.

<details>
<summary>Почему ключи подписывают только индексы</summary>

В `owfeed.yml` стоит `signing.sign-packages: false`. Фид не кладёт свою подпись внутрь пакета,
который собрал не он: раздаётся файл автора, байт в байт.

Доверие на роутере всё равно идёт из подписанного индекса. Установка, обновление и удаление по имени
были проверены и работают без единой подписи на пакете, в том числе через кнопки LuCI.

Не работает `apk add ./file.apk` и загрузка файла через LuCI. Им и для собственных пакетов OpenWrt
нужен `--allow-untrusted`.

</details>

## Добавление ключа в `keys/`

Это тот единственный диф в репозитории, который заслуживает второго взгляда. Запиненный ключ — то,
что вообще придаёт подписи смысл.

Проверяйте ключ вне канала — по чему угодно, кроме релиза, ради которого вы собираетесь ему
доверять:

- по репозиторию автора;
- по отпечатку, опубликованному в другом месте.

## Что намеренно не автоматизировано

**Публикация.** Плановая задача предлагает, но никогда не подписывает. Она может запустить `Publish`
для коммита, который уже в `main`. Push под `GITHUB_TOKEN` не поднимает событие push, и без этого фид
продолжал бы отдавать прежнюю версию. Ключа в этой задаче нет: он в том запуске, который она
стартует.

Задача, которая скачивала бы всё, что апстрим выложил с прошлого прогона, и подписывала, отдала бы
ключ фида всем апстримам сразу.

**Попадание в `main` — только если автор подписал, и не чаще двух раз в сутки.**
`AUTO_MERGE="yes"` доступен, только когда выполнено всё сразу:

- отделённая подпись проверяется против запиненного ключа;
- подпись формы покрывает изменившееся: `manifest` всегда, `apk` пока держится набор контейнеров,
  `binaries` никогда;
- это не третье обновление одного пакета за 24 часа.

Украденный ключ выпускает цепочку релизов быстрее, чем кто-либо читает уведомления, и каждый из них
проверяется безупречно. Всё, что за пределами этого набора, — pull request и мейнтейнер.

**Попадание в `main` чего-либо, кроме версии.** `land-updates.sh` отказывается пушить ветку, чей
диф против `main` называет любой путь, кроме `packages/<имя>/upstream.sh`. Так что `keys/`, `tools/`
и `.github/` для автоматики недостижимы. Это тот самый инвариант, который записан в `ECOSYSTEM.md` и
на который `.github/CODEOWNERS` просит ревьюера.

**Покрытие архитектур.** `owfeed.lock` фиксирует, для каких архитектур публикуется фид.
`--frozen-lock` валит сборку, когда список апстрима сдвинулся. Запустите `owfeed lock --update` и
прочитайте диф: то, что покрывает фид, — часть его договора с подписчиками.

### Почему автоматика обновлений устроена так

<details>
<summary>Почему доверенное обновление не открывает PR</summary>

Всё, что делает плановый job, происходит под `GITHUB_TOKEN`. Ни одно событие, которое обычно
поднимает запуск, под этим токеном не поднимается.

У pull request'а, открытого `app/github-actions`, создаётся запуск `pull_request`. Он встаёт в
`action_required`, пока его не одобрит человек. Формулировка GitHub: «when a workflow using
`GITHUB_TOKEN` creates or updates a pull request, the resulting `pull_request` event creates workflow
runs in an approval-required state».

Холд безусловен для этого токена. Политика репозитория `fork-pr-contributor-approval` **ни при
чём**. Её ослабляли до `first_time_contributors_new_to_github` на уровне репозитория и организации
одновременно. Бот-PR #60 всё равно получил `attempt 1 = action_required` (прогон 33966648498), и обе
политики вернули как было.

До этой организации холд докатился между 2026-08-30 20:43Z и 2026-09-01 10:08Z. Это измерено по
`attempts/1` прогонов на ветках `update/*` по обе стороны окна. На #45 ожидание составило двое суток.

Задержанный прогон — это pull request, который никто не проверил, поэтому каждое автоматическое
обновление ждало человека. Поэтому обновление, которое правила пропускают, PR'а не получает.

</details>

<details>
<summary>Почему гейт — <code>land-updates.sh</code>, а не защита ветки</summary>

`land-updates.sh` пушит только тогда, когда каждый прогон `check / build` и `check / check` на этом
коммите — `completed/success`. Контекст, у которого прогона нет вовсе, считается отказом. Диф не
должен называть ничего, кроме `packages/<имя>/upstream.sh`.

Обязательные проверки на `main` для этого включали и убрали обратно. При обоих зелёных контекстах на
коммите push всё равно отклонялся с `GH006: 2 of 2 required status checks are expected`. GitHub
засчитывает контексты для ветки, в которую пушат, а не для той, где они прогонялись.

Запуск `Check` идёт по голове ветки обновления. Check runs привязаны к коммиту, а не к событию.
Поэтому `land-updates.sh` читает эти контексты на том самом коммите, который собирается запушить.

Опубликовать такой запуск ничего не может. `pr.yml` передаёт `dry-run: true`, а publish-job в
`feed.yml` завязан именно на этот вход, а не на событие или ref. Никакой dispatch до окружения `feed`
не дотягивается.

</details>

<details>
<summary>Что по-прежнему требует человека</summary>

Обновление, которое под правила не подходит, пушится так же, но получает pull request, и его сливает
мейнтейнер. Не подходит — это любое из:

- нет подписи апстрима;
- форма `binaries`;
- смена мажорной версии;
- третье обновление одного пакета за сутки.

Автоматически не доезжает ничего за пределами `packages/<имя>/upstream.sh`. `land-updates.sh`
сравнивает ветку с `main` и отказывается пушить при любом другом пути. Новый пакет приносит ключ в
`keys/`, поэтому это pull request по построению.

</details>

<details>
<summary>Почему <code>Check</code> и <code>Publish</code> запускаются вручную</summary>

Push или мерж под `GITHUB_TOKEN` тоже не поднимает событие `push`. Поэтому `Publish` запускается
вручную, а не по триггеру. `workflow_dispatch` — задокументированное исключение в обоих случаях:
такие события всегда создают запуск.

</details>
