# Ранбук

*[English version](RUNBOOK.md)*

Эксплуатация фида. Про добавление и обновление пакетов — [CONTRIBUTING_ru.md](CONTRIBUTING_ru.md).

## Что когда запускается

| когда | что | ключ есть? |
|---|---|---|
| pull request | fetch → build → sign → index → check-tree → check-origin → sources → doctor → smoke (обе линии) | одноразовые |
| push в `main` | job 1: fetch → build | **нет** |
| | job 2: sign → index → check-tree → check-origin → sources → smoke → verify → publish → Pages | **да**, за `environment: feed` |
| раз в час | перевести `main` на любую ветку `update/*`, у которой обязательные проверки уже зелёные | нет |
| | спросить у каждого апстрима свежий релиз, запушить ветку обновления, если он есть | нет |
| | запустить `Check` на этой ветке: сам GitHub для неё запуск не создаёт | одноразовые |
| | открыть PR — только если обновление не из тех, что доезжают без человека | нет |
| | запустить `Publish`, если для головы `main` нет своего запуска `Publish` | нет |

Разделение на `main` — в этом весь смысл: fetch исполняет значения, пришедшие из pull request'а, и в
том job'е ключа нет. Ключ появляется, когда собранные байты уже лежат в артефакте.

Строка про pull request — не второй пайплайн, похожий на первый. Оба воркфлоу вызывают reusable
`feed.yml` из owfeed на одном и том же пине: `pr.yml` — с `dry-run: true`, `publish.yml` — с
`secrets: inherit` и без dry-run. Разница — одноразовые ключи, отсутствие environment и отсутствие
деплоя.

**Почему доверенное обновление не открывает PR.** Всё, что делает часовой job, происходит под
`GITHUB_TOKEN`, и ни одно событие, которое обычно поднимает запуск, не поднимается. У pull request'а,
открытого `app/github-actions`, запуск `pull_request` создаётся и встаёт в `action_required`, пока
его не одобрит человек, — «when a workflow using `GITHUB_TOKEN` creates or updates a pull request,
the resulting `pull_request` event creates workflow runs in an approval-required state». Холд
безусловен для этого токена. Политика репозитория `fork-pr-contributor-approval` **ни при чём**: её
ослабляли до `first_time_contributors_new_to_github` на уровне репозитория и организации
одновременно, и бот-PR #60 всё равно получил `attempt 1 = action_required` (прогон 33966648498);
обе политики вернули как было. До этой организации холд докатился между 2026-08-30 20:43Z и
2026-09-01 10:08Z — измерено по `attempts/1` прогонов на ветках `update/*` по обе стороны окна; на
#45 ожидание составило двое суток. С обязательными проверками на `main` такой pull request не может
слиться сам.

Поэтому обновление, которое правила пропускают, PR'а не получает. `check-updates.sh` пушит
`update/<пакет>-<версия>` и запускает на ней `Check`; следующий прогон `land-updates.sh` переводит
`main` на этот коммит fast-forward'ом. **Проверки при этом не исчезают:** защита ветки действует на
`main`, а не на pull request, и GitHub описывает этот путь прямо — «After all required status checks
pass, any commits must either be pushed to another branch and then merged or pushed directly to the
protected branch». Push с незелёными обязательными контекстами отклоняется с `GH006`.

Запуск `Check` идёт по голове ветки обновления; check runs привязаны к коммиту, а не к событию, —
поэтому он отдаёт те самые контексты `check / build` и `check / check`, которые читает защита ветки,
когда этот коммит пушат. Опубликовать он ничего не может: `pr.yml` передаёт `dry-run: true`, а
publish-job в `feed.yml` завязан именно на этот вход, а не на событие или ref, так что никакой
dispatch до окружения `feed` не дотягивается.

**Что по-прежнему требует человека.** Обновление, которое под правила не подходит — нет подписи
апстрима, форма `binaries`, смена мажорной версии, третье обновление одного пакета за сутки, —
пушится так же, но получает pull request, и его сливает мейнтейнер. И автоматически не доезжает
ничего за пределами `packages/<имя>/upstream.sh`: `land-updates.sh` сравнивает ветку с `main` и
отказывается пушить при любом другом пути, так что новый пакет, приносящий ключ в `keys/`, — это
pull request по построению.

Push или мерж под `GITHUB_TOKEN` тоже не поднимает событие `push`, поэтому `Publish` запускается
вручную, а не по триггеру. `workflow_dispatch` — задокументированное исключение в обоих случаях:
такие события всегда создают запуск.

**Как сюда попадает owfeed.** `owfeed/owfeed/setup@v0.5.0`, пин на релиз. Action скачивает один
бинарь и сверяет его с build-аттестацией из релизного workflow самого owfeed до запуска — не с
контрольной суммой из того же релиза, которую тот, кто подменил бинарь, подменил бы заодно. Раньше
это был `go install …@<sha>`: он компилировал инструмент в каждом job и не проверял ничего, потому
что доверяет тому, что module proxy отдаст за эту ревизию.

**Дождитесь релиза owfeed, прежде чем двигать пин.** `setup` сверяет бинарь с аттестацией из
релизного workflow самого owfeed и отказывается ставить тот, который не сверяется, — в том числе
тот, которого ещё нет. Пуш `setup@vX.Y.Z` здесь, пока тот релиз ещё собирается, роняет каждый job
с *«does not verify as built by owfeed/owfeed's release workflow»*: читается как атака, а на деле
гонка. Убедитесь, что релиз опубликован, и только потом двигайте пин.

**Пины пакетов двигайте тем же коммитом, что и политику, которая их требует.** Включить
`signing.author-keys`, пока пины указывают на неподписанные релизы, — значит исключить все пакеты
фида и опубликовать пустое дерево. Публикация при этом пройдёт успешно, а это худшая форма отказа.

Переход на новый релиз owfeed — две строки в `pr.yml`, две в `publish.yml` и две в `intake.yml`
(проверять `grep -rn 'v0\.' .github/workflows`, а не считать по памяти),
и это должен быть pull request, как всё остальное. Инструмент, который подписывает этот фид, должен двигаться, когда
кто-то поменял строку, а не когда запушили в чужой репозиторий.

**Две вещи в деплое на Pages, которые легко сломать.** `actions/upload-pages-artifact` нужен
`include-hidden-files: true` — с v4 он выбрасывает dotfiles, а `.nojekyll` это dotfile. Без него
Pages запускает Jekyll поверх дерева бинарей и убирает всё, что начинается с точки или
подчёркивания, из дерева, которое было корректным, когда его проверял `owfeed publish`. А
`actions/deploy-pages` нужен `actions: read`, который блок `permissions:` молча отбирает, назвав
другие области. `owfeed verify` сообщает **OWF514**, когда живой сайт потерял `.nojekyll`: снаружи
деплоя — единственное место, где этот ответ существует.

## Пакет пропал

`tools/check-tree.sh` запускается после `owfeed index` в обоих воркфлоу и валит прогон, если пакет,
который эта репа ингестит, отсутствует на релиз-линии, которую он объявляет.

Он есть потому, что этого больше никто не видит. `owfeed doctor` читает дерево и спрашивает, верно
ли то, что там лежит, — пакета, который не скачался, там просто нет, и все проверки зелёные. Так
дерево с одним пакетом из трёх на линии 24.10 однажды отчиталось готовым к публикации.

```
MISSING luci-theme-footstrap luci-theme-footstrap_0.11.6-r1_all.ipk on 24.10: absent from 36 of 36 architecture(s) (e.g. armeb_xscale)
```

Нет на **всех** архитектурах — фетч не дал ничего: в релизе нет такого ассета, либо в `upstream.sh`
не задан `ARTIFACT_IPK` у пакета, который раньше его публиковал. Нет на **части** — сборка не
доехала; ищите в логе шаг, который упал, не остановив прогон.

## Проверка красная

На pull request'е или на ветке `update/*` — один и тот же workflow отчитывается в обоих случаях.
Читайте находку. Каждая говорит, чем это грозит и что делать. Те, у которых причина неочевидна:

**`OWF207` — конфигурация шипается, но не объявлена.** Пакет ставит `/etc/config/foo`, а в
`conffiles:` его нет. sysupgrade читает `.conffiles_static`, чтобы решить, что переживёт обновление
прошивки, — значит настройки пользователя будут заменены вашими дефолтами при каждом обновлении, и
никто об этом не сообщит.

**`smoke` упал, а `doctor` прошёл.** Дерево согласовано, а роутер его не принимает. Смотрите вывод
контейнера: обычно это зависимость, которая не резолвится на стоковом образе, или файл, положенный
туда, куда никто не смотрит.

**`sha256 … pinned …`** на шаге fetch. Апстрим подменил релиз на месте. Не правьте пин, чтобы
прошло, — сначала выясните, почему изменились байты.

**`NO ORIGIN …`** от `tools/check-origin.sh`, после сборки индекса. Пакет дошёл до дерева, не сказав,
откуда он, и этот фид его не публикует. Здесь это не чинится: поле ставится там, где пакет
собирается, так что ответ — письмо апстриму. Значение вида `feeds/base/<name>` валится так же, как
пустое: это путь, из которого собирал SDK, а не место, куда можно пойти.

## Появилось обновление, а версию я не узнаю

Посмотрите диф — неважно, пришёл он pull request'ом или коммитом в `main`: там должна быть версия и
её суммы, больше ничего. Если задето что-то ещё — проблема в боте, а не в релизе; причём
`tools/land-updates.sh` такой push бы отверг, так что в `main` эта форма означает, что коммит
положил человек.

Отключить самообновление пакету — `AUTO_MERGE="no"` в его `upstream.sh`. Это единственный надёжный
способ придержать обновление: доверенное доезжает примерно за два часа после публикации апстрима, и
закрывать там нечего. Для обновления, которое всё-таки получило pull request, работает прежнее:
закройте его — бот не переоткроет и ветку не пересоберёт.

**Ветка `update/*`, которая не доезжает,** — это красная проверка, и лечится чтением прогона. В логе
часового job'а бывают ещё две формы: `not green yet` с контекстом в состоянии `cancelled` — удалите
ветку, следующий часовой прогон пересоберёт её и запустит проверки заново, — и `REFUSED`: ветка
трогает путь, которого обновлению трогать нельзя, и это уже к человеку.

## Публикация упала

Публикация — отдельный job с ключом. Частые причины:

**`$OWFEED_SIGN_KEY is empty`.** Секрета нет, или прогон стартовал раньше, чем секрет появился.
Перезапустите job.

**`owfeed verify` сообщает `OWF513`.** Уже опубликованная версия имеет другое содержимое, чем то,
что её заменяет. Либо пакет изменился без поднятия версии, либо сборка перестала быть
воспроизводимой — проверьте, что `SOURCE_DATE_EPOCH` всё ещё выставлен в воркфлоу. Не публикуйте
поверх: поднимите ревизию.

**Pages не обновились.** Деплой делает `actions/deploy-pages` — смотрите тот job, а не фид.

## Посмотреть, что видят подписчики

```sh
owfeed verify                 # по задокументированному URL, локальное дерево не нужно
owfeed verify out             # плюс сравнить то, что заменит опубликованное
```

Забирает опубликованный ключ и индекс и сообщает о редиректах, по которым apk не пойдёт; о пакетах,
которые живой индекс называет, а их нет или они другого размера; и о версиях, перепубликованных с
другим содержимым.

С точки зрения роутера, одной командой:

```sh
owfeed smoke                  # ставит собранный фид на живой образ OpenWrt
```

## Ключи подписи

Их два, потому что каждый пакетный менеджер проверяет только свою схему:

| секрет | схема | что подписывает |
|---|---|---|
| `OWFEED_SIGN_KEY` | EC prime256v1 | apk-индекс |
| `OWFEED_USIGN_KEY` | usign / ed25519 | opkg-индекс |

Оба подписывают **только индексы**. В `owfeed.yml` стоит `signing.sign-packages: false`, поэтому фид
не кладёт свою подпись внутрь пакета, который собрал не он: раздаётся файл автора, байт в байт.
Доверие на роутере всё равно идёт из подписанного индекса — установка, обновление и удаление по
имени были проверены и работают без единой подписи на пакете, в том числе через кнопки LuCI. Не
работает `apk add ./file.apk` и загрузка файла через LuCI, которым и для собственных пакетов OpenWrt
нужен `--allow-untrusted`.

Оба живут в секретах репозитория и больше нигде здесь. `.gitignore` закрывает `*.pem` и `*.sec`,
чтобы их нельзя было закоммитить случайно.

opkg-ключ публикуется под своим id в качестве имени файла — именно так opkg его ищет. apk-ключ
публикуется под именем фида, потому что apk сопоставляет по идентичности внутри подписи, а имя
игнорирует.

**Отзыва не существует.** У apk нет ни CRL, ни срока годности, ни способа сказать «ключ мёртв». Если
ключ утёк, каждому подписчику придётся поставить новый руками — пути, который дотянется до роутера,
выключенного в нужный момент, нет.

Ротация: сгенерировать новый ключ, опубликовать оба публичных на время перекрытия, подписывать
индекс обоими, потом убрать старый. apk сопоставляет ключи по идентичности, а не по имени файла, так
что несколько ключей сосуществуют на устройстве и перекрытие ничего не стоит. Команды в owfeed для
этого пока нет; шаги описаны в его дизайн-документе.

## Добавление ключа в `keys/`

Это тот единственный диф в репозитории, который заслуживает второго взгляда. Запиненный ключ — то,
что вообще придаёт подписи смысл, поэтому проверяйте его вне канала: по репозиторию автора, по
отпечатку, опубликованному в другом месте, — по чему угодно, кроме релиза, ради которого вы
собираетесь ему доверять.

## Что намеренно не автоматизировано

**Публикация.** Ежечасная задача предлагает, но никогда не подписывает. Что она может — запустить
`Publish` для коммита, который уже в `main`: push под `GITHUB_TOKEN` не поднимает событие push, и без
этого фид продолжал бы отдавать прежнюю версию. Ключа в этой задаче нет — он в том запуске, который
она стартует. Задача, которая скачивала бы всё, что апстрим запушил за час, и подписывала, отдала бы
ключ фида всем апстримам сразу.

**Попадание в `main` — только если автор подписал, и не чаще двух раз в сутки.**
`AUTO_MERGE="yes"` доступен только там, где отделённая подпись проверяется против запиненного ключа,
только для форм, чья подпись покрывает изменившееся (`manifest` всегда, `apk` пока держится набор
контейнеров, `binaries` никогда), и никогда для третьего обновления одного пакета за 24 часа.
Украденный ключ выпускает цепочку релизов быстрее, чем кто-либо читает уведомления, и каждый из них
проверяется безупречно. Всё, что за пределами этого набора, — pull request и мейнтейнер.

**Попадание в `main` чего-либо, кроме версии.** `land-updates.sh` отказывается пушить ветку, чей
диф против `main` называет любой путь, кроме `packages/<имя>/upstream.sh`, — так что `keys/`,
`tools/` и `.github/` для автоматики недостижимы. Это тот самый инвариант, который записан в
`ECOSYSTEM.md` и на который `.github/CODEOWNERS` просит ревьюера.

**Покрытие архитектур.** `owfeed.lock` фиксирует, для каких архитектур публикуется фид, а
`--frozen-lock` валит сборку, когда список апстрима сдвинулся. Запустите `owfeed lock --update` и
прочитайте диф: то, что покрывает фид, — часть его договора с подписчиками.
